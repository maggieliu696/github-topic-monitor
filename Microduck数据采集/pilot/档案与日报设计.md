# robotic harness 项目记录与日报

## 一个项目，只读一份记录

每个项目只有一份可读文档，以实际项目名称命名，平放在[项目记录入口](output/索引.md)。不再拆成项目卡、完整档案、来源清单、问题文档和变化日志，让读者来回跳转。

文档直接写四部分：

1. **项目做什么**：作者、目标人群、用途、分类、开源情况、已取得的最新版本和 Star 数。数据注明日期。
2. **目前做到哪一步**：实际功能、作者的测试结果、尚未实现的计划，以及我们当前如何理解。
3. **遇到的问题和处理**：谁遇到了什么，作者怎样回应或修改，有没有使用者确认恢复。未解决的问题也写在这里。
4. **按日期记录进展**：同一篇里持续追加新版本、实质改动、问题解决过程和 Star 变化。重要判断改变时，说明原来怎么理解、新证据改变了什么。

每段在需要处直接附原始链接，不要求读者另开证据文档。技术词只保留理解项目所必需的部分，并用普通话解释。正文不用内部编号，不设三级标题，不按每条证据拆成卡片。

## 更新怎么写

新资料读完后，更新文档前面的当前情况，在末尾追加带日期的进展。既有进展保留，不把整篇再复制成一个新文档。正文问题也同步更新状态，例如“作者称已修复，尚未得到原提问者确认”。

区分原文的发布日期、资料采集日期和整理日期。首次发现历史项目写“首次收录”，不能写成当天新发布。Star 只有两次可比记录时才计算增减，同时写明比较日期；只有一次记录就保留当次数值。

## 先初始化，再每天更新

当前仅监控GitHub，已完成40项目批次、累计41份记录。剩余84项候选未自动初始化；新增项目按同样规则建档。先核对名单和跨平台归属：同一个项目只建一篇记录，讨论帖和配套模型并入对应项目；无明确归属的讨论保留为线索，不凑成独立项目。

初始化读取当前说明、版本和重要问题及回复，形成每项目一篇的起始记录。保留用途、作者、功能、实验条件、结果、问题、解决过程、评价、限制和来源；可以合并重复表述，但不因统一字数删掉改变判断的信息。没有取得的资料注明缺口。初始化材料是用于以后比较的起点，不当作当天的新进展。

初始化完成后，每天北京时间上午9点按顺序处理：

1. **检查已有项目**：比较说明、版本、问题与回复等资料，只深入分析有变化的部分及必要上下文；更新同一篇项目记录，不每天重写全部项目。
2. **搜索新项目**：在GitHub搜索新作品和新讨论，与已有名单去重；符合范围的项目建立同样的简单记录。区分新发布和今天才发现的旧项目。
3. **汇总变化**：把已有项目进展与新项目放回研究方向，合并共同问题，识别重要解决办法、失败、反例、新用途和新分支，再写日报。

没有检查成功的来源记为未完成，不写成没有更新；检查进度和原文留在后台，不堆进项目正文。

## 日报是汇总层

**项目记录回答“这个项目具体怎么样”；日报回答“今天各方向发生了什么值得关注的变化”。** 日报不逐个复述项目简介，也不拼接一百多份记录。

开头一两句写最重要的发现；随后按有重要变化的方向，用约3至5条讲清新增了什么、什么问题有进展、这意味着什么。每条通常2至4句，必要时点名1至2个项目并链接其记录或原始来源。安装步骤、完整实验参数和问题往来留在项目记录中。

同一问题在多个项目出现时合并说明；只有一个项目的发现明确限定在该项目，不自动写成趋势。低频但重要的新想法或反例也可进入日报。日常稿简洁，整体观察按已确认定稿展开，篇幅按实际重要性调整，不为凑篇幅或栏目重复旧信息。

结尾用一句话说明实际检查范围及重要缺口。没有重要更新时不重复推送；阅读入口保留最近一期日报及其原日期。

原始 API 数据、来源历史、内部编号及研究判断版本继续在后台保存，供核对和恢复，不再自动生成多层阅读文档。当前已完成四类各十个项目的初始化，累计41份项目记录；剩余项目的全量初始化及每日自动流程尚未运行。
