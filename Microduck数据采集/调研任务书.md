## 当前范围（2026年10月26日确认）

当前只监控 GitHub。Hugging Face、Hacker News 的既有材料作为历史来源保留。现有 41 个 A 级项目、80 个 B 级 GitHub 项目，另有两个官方背景仓库。自动采集、分析和飞书推送已接通。

## 要回答的问题

持续观察Microduck的各个开发方向怎样发展：有哪些项目加入，大家在解决什么问题，哪些问题有了进展，以及出现了哪些新想法和方向分支。每个方向内同时记录开发者的用途、实际问题、产品评价和交流入口，为后续找到值得交流的开发者和需求方向提供依据。

本阶段观察对象包括独立开发者、开源贡献者、机器人爱好者以及相关技术讨论参与者。仅凭账号或项目不能判断作者是否独立创业；能够核实的公司、官方团队或组织背景另行标注。购买自述作为补充线索，不估算销量、全部买家分布或满意度。

## 按研究方向组织报告

报告的一级板块是“大家围绕鸭子在做哪些方向”，项目归入方向，日常更新也归入方向。用途、问题、评价和交流入口作为各方向内部的观察内容。

沿用前一轮125个项目的主分类，起步设四个方向。以下数量是2026年10月26日前轮研究的样本基线，不是本轮新增项目数，也不代表全网规模。

| 方向编号 | 方向名称 | 用普通话说，在研究什么 | 前轮项目数 |
|---|---|---|---:|
| D01 | 动作训练与算法实验 | 怎样让鸭子学会动作、保持稳定，怎样验证和复现训练结果 | 35 |
| D02 | 开发工具与运行环境 | 怎样让安装、控制、训练、调试和学习更方便 | 35 |
| D03 | AI应用与交互玩法 | 怎样让鸭子听懂、看懂、回应人，参与具体任务或游戏 | 32 |
| D04 | 硬件复刻与适配 | 怎样组装或改造实体鸭子，适配零件并提高可靠性 | 23 |

每个方向下面可以再细分。例如动作方向可细分为行走、起身、踢球等；应用方向可细分为语音互动、视觉任务、桌面宠物等。这些是分支示例，尚未完成125个项目的逐项分支编码，不能当作完整的分支数量统计。

累计报告在每个方向内写清：当前有哪些项目和分支、共同关注什么问题、已有进展与待验证之处、新想法，以及参与者明确的评价和交流入口。主要观点尽量配1到2个案例及原链接，并保留最后更新日期。

报告末尾另附“数据与边界”，交代采集范围、去重方法和缺失来源。结论仅覆盖实际观察到的参与者，不能推广到全部购买者或所有平台。

## 项目怎样编码到方向

每个正式纳入项目只维护一份可读记录，以真实项目名称命名，平放在同一目录。用途、现状、问题和按日期追加的进展都写在这篇里；来源直接放在对应段落之后。以下字段继续在后台保留，内部编号不展示在正文。信息不足时写“未披露”或“待核实”，不编造。

| 必填项 | 编码要求 |
|---|---|
| 这个项目是做什么的 | 用普通中文说明具体用途、功能和服务对象 |
| 当前这个项目的结论 | 根据现有证据说明已经做到什么、验证到哪一步、当前能支持什么判断；区别作者自述与本研究核验，附核对日期 |
| 发现了什么问题 | 写清具体问题、发生条件及未解决／已有办法／已解决状态；计划中功能和待验证事项单独标注，不当作已发生故障 |
| 分类 | 固定主方向编号与名称；有依据时补充细分分支或描述标签 |
| 在本分析项目中的编号 | 沿用固定P编号；跨平台还是同一编号，DEMO序号和平台帖子ID都不能替代它 |
| 作者名称 | 记录公开署名／账号／组织名，注明身份类型；不能据账号推断真实姓名或将发布者当作唯一贡献者 |

记录结合项目说明、问题帖和作者回复，不能只读介绍就断定没有问题。正文用普通话写清作者、服务对象、用途、开源情况、已取得的最新版本、Star数、当前能力、问题及处理、评价和未验证事项；不拆成多个阅读文档，不使用三级标题或证据卡片。

新资料先更新前面的当前情况，再在同一篇末尾按日期追加实质变化及来源。原文日期与采集日期分开，首次收录不当作新发布。Star注明观察日期；有两次可比采集才计算涨幅，并说明比较区间。原始全文、来源历史和内部研究判断版本作为后台数据保存，不再生成供人跳转的Markdown目录。判断改变时，在项目记录的更新段落直接解释旧判断、新证据和新判断。

每个项目有一个长期不变的项目编号和一个主方向。既有项目沿用原P编号，并把原主分类对应到D01至D04；不会因为每天换了关键词、发布平台或新增一条评论就重新分类。同一项目在不同平台出现，合并到同一个项目编号。

新项目根据作者说明的主要目标和核心产出确定主方向，同时保存归类理由和证据。跨方向项目可以加辅助标签，但项目数量只在主方向计一次。材料不足或确实不适合现有方向时，先标“待归类”，不硬塞入四类。只有项目目标发生实质变化，或原分类有误时才调整主方向，并记录原分类、原因和日期。

分支使用所属方向下的固定编号，例如D01-01。项目可以暂时没有分支；新增分支须说明它要解决的独立问题、与已有分支的区别及来源依据。单个新想法先作为“想法线索”，不能直接写成已有项目或成熟分支。材料显示有独立目标但尚缺实现时，可标“候选分支”；有具体实现和清楚边界后，再正式纳入。单个项目形成的分支不描述成已经有一群人在参与。

同一个问题也要持续追踪：记录涉及哪些项目、已有办法、未解决部分和最新证据。至少在两个独立项目或作者中核实后，才称为本样本中“多方关注的问题”；只有一个项目披露时，写“该项目遇到的问题”。跨方向的问题可以互相引用，但不因此重复计算项目数。

## GitHub采什么

先检查已建档项目，再搜索候选名单外的新项目。读取项目说明、版本发布、公开问题及回复，补充 Star 和观察时间；保留正文、作者、原链接、发表或更新时间、采集时间、上下文与变化记录。配套仓库合并到同一项目；代码合并请求不能直接当作用户问题。

使用 Microduck、micro duck、micro-duck 等关键词和已有项目链接发现线索，再阅读内容确认相关性，不按关键词自动决定收录或分类。当前候选清单保留历史来源，正式跟踪清单由已有41份记录生成，两个官方仓库只作为背景，不计入41个项目。

## 连接和执行边界

当前方式是官方 API 主动读取，已配置 GitHub Token 和每日定时任务。流程为“已有项目回查→新项目搜索→阅读分析→更新记录和总表→日报编辑”。

只读凭证通过本地环境变量提供，不写进配置或日报。匿名额度不足时保留待办和缺口，不能把未检查写成没有更新。分支项目必须读取对应分支；README链接到外部平台只作为待核查线索，当前采集不自动扩展到其他平台。

旧版采集器已能读取GitHub资料、保存变化和搜索候选，但还没有把已建档名单、分支说明、全部配套来源、研究判断与日报形成完整的日更链条。具体未接通项见[项目流程与检查结果](../项目流程与检查结果.md)。历史三平台API试取记录见[连接流程](连接流程.md)，不作为当前范围。

## agent收到变化后怎样判断

每次判断同时读取三部分：本次变化及上下文、项目上一次的记录、所属方向的现有问题和结论。只读一条推送不足以判断结论是否改变。

先由程序合并重复通知、定位变化内容；agent再按以下顺序判断。规则不采用一个笼统的重要性分数，每一步都留下简短理由。

| 判断步骤 | 判断依据 | 处理结果 |
|---|---|---|
| 1. 是否相关、是否真的有新内容 | 是否属于Microduck研究范围；与上次正文相比改变了什么；是否只是重复转载、格式或计数变化 | 无关或无实质变化只保留处理记录。仅有代码变化不能直接当作噪声，要看是否改变功能、实验或限制 |
| 2. 证据是否足够理解 | 能否取得原文及回复上下文；是谁提出、在哪个环境测试；是计划、实现、失败还是修复 | 不足时列为待核实，补取上下文后重判。可把“作者提出某想法”收为想法线索，但不能写成已实现 |
| 3. 是否进入研究档案 | 是否新增或修正用途、项目进展、问题、方法、验证、评价或新想法 | 有实质信息就收录，关联固定项目、方向、分支和具体问题。保存原文、链接、时间及收录理由 |
| 4. 是否值得进入日报 | 是否有值得关注的新项目、能力进展、反复问题的新办法、独立验证、反例、新想法或分支 | 对理解该方向有新增价值时进入日报；重复佐证旧判断、无明显新增意义的材料只补档案。反例与失败同样可以重要 |
| 5. 是否影响方向结论 | 新证据是否支持、反驳、限制或补充某条现有结论，验证环境是否可比 | 分别记录结论未变、新增结论、扩大或缩小适用范围、撤回原判断；不能因为收录了项目就自动改变方向结论 |

“保存材料”“纳入研究”“进入日报”“修改结论”是分别判断的四件事。一条信息可以进入日报，但方向结论仍然不变；也可以作为重要反证，直接促使原结论收窄。低频的新想法不因讨论人数少被过滤掉，但应标明只是线索。

每条方向结论保留固定编号、原文、适用条件、支持与反对证据、最后核对日期。修改时保存“原判断→新判断→修改原因→依据”。不能用帖子数量、点赞量或作者一句“已修复”直接推出普遍有效；多个同源转载也不是独立验证。明确的反例即使只有一条，也可能足以推翻原先过强的概括。

例如，以下仅为判断流程示例：动作训练项目新增一条“踢球后站不稳已修复”的通知。先读修复说明和测试结果；若只验证了一个仿真条件，就收录为“该项目报告在指定仿真条件下改善”。若此前其他项目也在讨论类似问题，可列入日报作为新办法；当前方向结论仍保留实机和跨项目验证缺口。若后续独立作者复现，再增加证据或调整结论适用范围。

每条处理结果至少保存：方向及项目、变化摘要、证据链接、是否收录、是否进日报、关联哪条结论、结论如何处理、理由和待核实事项。新来源或新分支暂不适合现有编码时标待归类，不丢弃。

## 首次回溯和以后更新

建议首次将现有项目的当前说明存下来，形成用于比较的起点。GitHub的问题与讨论优先读取最近30天更新的内容，并补充仍未解决的问题。最近30天是建议的起步范围，可由你调整。

以后每天同时做两件事：发现名单外的新项目或讨论；检查已收录来源的正文、回复和状态有没有变化。新增回复可能出现在旧帖子下，因此不能只找今天发布的帖子。重要的问题解决记录也应追踪，避免只收集抱怨。

每条资料保存平台、项目或主题、原链接、公开作者署名、正文、发表或更新时间、采集时间，以及回复对应的上文。平台未提供更新时间时标为未知，不拿采集时间代替。首次入库和平台当天新增分别统计。

## 纳入与排除

纳入作者对具体项目、用途、实验、问题、修复或产品取舍的实质表述。官方资料与第三方实践分别标记。真实硬件、复刻硬件、电脑仿真和未验证计划分开解释。

目录、新闻汇总、自动生成榜单、重复转载和无实质改动的分叉，保留为候选线索，不直接纳入开发项目统计。模型、数据集和配套仓库可能属于同一项目，需要合并。发布账号不等于独立自然人，项目存在不等于已经购买。

同一个项目在GitHub和Hugging Face都有页面时，通过作者提供的项目链接等明确证据合并；只有相似昵称时不合并账号。不同作者重复讨论同一个问题，可用于说明反复出现，但同一篇转载不重复计数。

## 分析规则

每个主要判断必须有原文片段和可打开的来源链接。分析时读取上下文；“尚未测试”“计划支持”“已经失败”“已经修复”分别标记。没有明确表达意见，就保留未知。机器人故障、依赖报错与作者对产品的总体评价分开。

按前述四个方向和编码规则整理项目；Python不凭关键词自动确定研究方向。主题、问题和评价允许交叉，不能把重叠次数换算成用户比例。前轮分类保留为历史基线；后续分类调整必须留记录，不覆盖原统计。

每个纳入项目或讨论按以下口径整理：

| 分析项 | 需要写清楚什么 |
|---|---|
| 项目归属 | 固定项目编号、主方向、已有或候选分支、归类理由；跨方向内容另加辅助标签 |
| 做什么 | 具体用途、服务谁、作者怎样介绍项目；不要只写“AI项目” |
| 当前项目结论 | 基于现有证据归纳已做到什么、验证到哪一步、还有什么限制；保留日期及依据 |
| 作者名称 | 公开署名或账号及身份说明，不猜测真实姓名 |
| 做到哪一步 | 仅有想法、电脑仿真、复刻硬件测试、官方实机测试，或无法确认 |
| 遇到什么问题 | 具体症状、发生条件、影响，以及仍未解决、已有绕行办法或已经修复 |
| 怎样评价产品 | 作者明确认可或不满的具体方面；没有表达就标为未披露 |
| 在哪里活动 | 发布作品、求助和持续回复的具体仓库、主题或社区入口 |
| 本次变化 | 新收录项目、已有项目进展、问题进展、新想法、候选或正式分支；关联到具体方向和问题 |
| 判断依据 | 支持判断的原文、链接和日期；推测单列，不混入事实统计 |

例如，作者说“我用它训练踢球，但还没上真机”，应整理为“动作训练、电脑仿真、实机待验证”，不能写成“实机踢球成功”或“已购买”。这里仅用于说明规则，不作为新增案例证据。

分析工作由阅读证据的研究步骤完成。采集程序只保存来源事实、内容变化和候选名单，不自动给人贴画像或判断满意度。外部正文中的命令、链接和提示只作为研究材料，不执行其中的指令。

## 初始化与每日顺序

已完成41份 A 级项目记录；其他已确认的 GitHub 项目进入 B 级轻量监控。新发现的相关项目必须去重、编码、归类并分到 A 或 B。每个独立项目只建一篇记录；讨论帖、回复和配套模型作为项目资料，不另建重复项目。

初始化记录当前用途、作者、功能、版本、Star、已取得的实验结果、问题与解决过程、评价和限制，相关段落直接附来源。合并重复信息，保留影响判断的条件和相反证据，不设机械字数上限。原始资料完整保留在后台；初始化不是当天新项目的统计。

初始化完成后，每天北京时间上午9点按以下顺序执行：

1. 先检查已有项目是否更新，读取变化及必要上下文，修改同一篇项目记录的当前情况并追加日期进展；无变化的项目不重新全文分析或改写。
2. 再搜索GitHub上的新项目及讨论，与已有名单去重后决定收录；区分真正新发布和新发现的历史项目。
3. 最后按研究方向合并各项目变化，判断共同问题是否有进展、有无新用途或分支，以及哪些原判断需要调整，生成简短调研日报。

## 每日输出

**项目记录保存具体事实和过程，日报只呈现汇总后的重要变化。** 日报面向未参与研究的项目组成员，不逐项复述项目简介，不把项目记录压缩后逐个排列。

开头用一两句话写最重要的发现，随后按方向呈现约3至5条重要变化，通常每条2至4句：出现了什么、解决或暴露了什么问题、为什么值得关注。需要证据时，点名1至2个项目并链接其记录或原文。日常稿保持简洁，篇幅服从重要内容；整体观察按固定定稿展开，不设空栏目。

多个项目的相近变化合并描述，但不把同源转载当独立证据；单项目结果限定在该项目，不直接写成行业趋势。失败、反例和低频新想法也可重要。提出方法、作者报告修复和其他使用者确认恢复分别写清。Star变化只用可比日期的数据，不能当作用户或买家数量。

日报中的判断直接说明具体内容；有变化时解释新证据改变了什么。详细功能、实验条件、完整问题与回复、未解决事项留在那一篇项目记录中。正文使用项目名与方向名，不显示内部编码和处理日志。

结尾简述实际检查范围和影响理解的重要缺口。未成功检查不等于没有更新。没有值得关注的变化时不重复推送；阅读入口保留最近一期全文及原日期。

详细规则见[项目记录与日报设计](pilot/档案与日报设计.md)。现已完成四个大类各取 Star 前十的40项目批次，累计41份项目记录；剩余项目的全量初始化及上述每日自动流程尚未执行。

## 按需生成阶段调研报告

阶段调研报告与日报是两种交付物。日报回答“本轮出现了什么重要变化”，阶段调研报告回答“截至指定日期，这个领域整体发展到哪里”。阶段调研报告不定时自动发送，由用户在汇报、复盘或决策前提出后生成。

生成阶段调研报告时，必须重新读取当时全部监控项目的当前记录、汇总清单、重要变化和未解决问题，不能把历期日报直接拼接成报告。报告至少包括：样本范围、各方向在关注什么、目前做到哪一步、共同问题、参与者评价、值得关注的机会、后续观察重点和证据边界。主要判断配1至2个公开案例链接，用普通中文写成可以直接向他人讲解的完整报告。

报告标题和正文写明时间点，并保存为独立版本。旧版本不覆盖，便于以后比较不同时间点的领域状态。首份版本为[2026年10月26日初始报告](../交付包/robotic%20harness%20领域调研报告_初始版_20261026.md)。

## 日报最后的中文润色

**这是用户已确认的交付要求，每一期必须执行，不能只凭“写得简短”判断合格。** 默认读者不了解机器人、编程和机器学习，也没读过之前的研究。日报写给项目组成员，不能要求他们先看项目文档才理解正文。

固定参照[用户认可的通俗样稿](writing-skills/日报风格基准.json)。该文件保存三项目阶段的写法，只用于对照语言；其中的事实、数量和日期不带入新日报，也不随新日报覆盖。以下是必须遵守的要求：

1. **先讲人和具体事情。** 说清谁想做什么、已经做到了什么、碰到了什么麻烦、后来怎样了。英文项目名只帮助找到出处，不能代替用途说明。例如“有人想直接买焊好、测过的电路板”，比“出现配套硬件需求信号”更清楚。
2. **把术语换成读者能理解的事情。** 用“自己买零件组装”“先在电脑里试动作”“作者说改好了，但还没有使用者回来确认”。确实需要专业词时，同一句解释；不把术语换成另一组术语。实验参数、版本号、内部编号和完整排查过程留在项目记录里，除非它们直接影响本期判断。
3. **按方向讲重要发现或变化，不逐个介绍全部项目。** 标题直接说明这件事，如“自己组装：有人想直接买配好的零件”。每条通常2至4句，用1至2个项目支撑；不机械套用“这说明／值得关注／下一步”的相同结尾。
4. **用自然、连贯的中文。** 像向不懂技术的同事解释一件事，保持专业、平实。避免口号、宣传语、抽象标签和无依据的市场判断；也不为了显得简单而幼稚化、使用含混比喻或省掉解释。
5. **简洁，但保留改变理解的条件。** 分清电脑里的模拟与实体机器人，作者说成功与使用者确认成功，购买咨询与实际成交。首次收录历史资料写“首期观察”，不能写成“今天新增”；一个人的问题不能写成所有用户的需求。
6. **篇幅与来源。** 日常稿保持简洁，整体观察允许展开，不设机械字数上限。开头一两句话讲重点，随后只列有内容的方向。来源跟在相应段落后，正文不放处理日志。没有重要更新就不凑日报。

每次生成时，先阅读本节、固定样稿，以及项目内固定版本的 [Humanizer-zh SKILL.md](writing-skills/humanizer-zh/SKILL.md)；按现有证据筛选、汇总出简稿，再应用该 skill 润色。不调用问题整理师参与这一环节。使用 skill 是实际读取并按规则编辑，不是在元数据中填入名称就算完成。

交付前逐段核对：没学过编程的人能否读懂发生了什么？是否有术语需要他自行查找？是否仍像项目介绍清单、测试报告或流程说明？是否改变了原文的数字、日期、归因、范围或完成状态？有问题就改，不能把这些检查留给读者。最后只展示成稿，不附自评分或内部检查表。

后台保存所用样稿、skill和最终文本的文件指纹，以及本期来源范围，方便核查。这里约束语言编辑与交付检查，不表示已开启定时采集或自动推送。

## 推送排版与内容取舍（2026年10月26日用户确认）

40个项目的汇总阅读测试已获用户认可。固定采用[本次推送定稿](writing-skills/日报推送定稿.md)作为内容层次和Markdown排版的参照；此前三项目[通俗样稿](writing-skills/日报风格基准.json)继续作为语言参照。新日报只参照写法和排版，不复用历史事实冒充新进展。

- 一级标题放项目名、日报和日期；开头用引用块概括主要发现，直接进入内容。
- 各板块用二级标题“01 · 方向名称”，下一行用一句加粗的话说明主要发现。板块之间用分隔线，段落之间留空行。正文只加粗少量核心判断，保持连贯叙述。
- 相关来源在对应段落后单列“参考：”链接，便于阅读和追溯；末尾保留简短、斜体的资料说明。
- 不再加入用户已删除的“本期首次观察、四类各选十个”的开场方法段，也不加入“下一轮优先看三件事”的结尾工作计划。采集范围和选样方法仍保存在后台，不能因此把旧资料写成当天新进展。
- 内容按共同方向、不同做法、具体困难和重要新尝试来取舍，不机械地每类只选一个案例，不为了300至600字限制删去重要发现。整体观察可以适当展开；日常只写重要变化，没变化的板块不凑数，编号按本期内容顺排。
- 当前确认的是40个项目的汇总内容与推送样式，不是40个研究方向，也不表示每日采集或自动发送已经启用。

## 接入前的检查标准

你检查这份任务书后，再把确认的范围同步到配置和采集程序，启用定时任务。检查重点是：四个方向是否符合你想看的动态；项目归属是否清楚；每个平台的资料是否够用；最近30天的起步范围是否合适；日报能否指出各方向新增了什么、解决了什么或提出了什么。

接入试运行应能够回查每个主要判断的原文；同一项目跨平台仍只有一个主方向和项目编号；重复通知不重复收录；断线、漏通知或权限不足后能补查并报告缺口；正文、功能或问题状态变化能够识别并归到方向；新想法与已实现项目分开；每次收录、日报选择和结论变更均有依据。达到这些标准后，再进入每天运行。

### 汇总表里的 GitHub 关注度

GitHub 项目在汇总表中同时显示 Star 数和采集日期，保留原有用途、调研价值和证据。数字从官方 API 的 stargazers_count 字段读取。每次采集保存原始响应及时间，只有同一仓库两次有效观察才计算变化，并注明比较区间；不是每天采集的记录不称为“日增长”。分支或子目录使用整个仓库的 Star，必须标明；非 GitHub 项目写“不适用”，获取失败写“待补采”或保留带日期的旧值，不能填 0。
